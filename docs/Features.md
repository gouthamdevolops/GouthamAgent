# Key Features

This document highlights the core features, fixes, and design decisions implemented in **GouthamAgent** to make it robust, resilient, and accurate.

---

## 1. Meticulous SQLite & Dialect Safeguards
SQL dialects differ significantly. SQLite, in particular, has specific behaviors that frequently cause standard agents to fail:
- **SQLite Double-Quotes Quirk**: In SQLite, double-quoting a non-existent column name (e.g. `"IsRelease" = true`) evaluates as a string literal instead of throwing an error. This silently returns an empty list `[]` instead of letting the agent know a column name is wrong. GouthamAgent's prompt strictly mandates validating schemas before executing complex queries.
- **SQLite JSON Extraction**: Standard columns cannot be queried directly if they contain JSON strings. GouthamAgent uses SQLite-specific JSON extraction functions (e.g., `json_extract(VersionInfo, '$.IsRelease')`) to parse fields within JSON columns.

## 2. Sandbox Variable-Name Sanitization
When using OpenRouter APIs, tool call IDs generated by the LLM often contain dashes (e.g., `chatcmpl-tool-8a25f14e...`). 
- **The Issue**: The base framework used raw IDs as python variable names inside the sandbox (e.g., `var_chatcmpl-tool-8a25f14e = SmartVariableList(...)`). In Python, dashes are interpreted as subtraction operators, causing immediate `SyntaxError: cannot assign to expression` crashes.
- **The Solution**: GouthamAgent modifies the orchestrator in [DataAgent.py](file:///D:/Goutham_DataAgentBench/Source_Code/DataAgent.py) to replace all dashes in variable names with underscores:
  ```python
  result_key = f"var_{tool_call.id}".replace("-", "_")
  ```
  This creates valid Python identifiers (e.g. `var_chatcmpl_tool_8a25f14e`), making sandbox executions reliable.

## 3. Large Data Stream Handling
When database query results exceed 2,000 characters, GouthamAgent writes the full output to a JSON file (e.g., `file_storage/<tool_call_id>.json`) and only returns a preview of the first 2,000 characters to the agent's context window. 
This prevents the context window from filling up quickly and reduces API token costs.

## 4. Lazy-Loaded Python Variables
To query these large data results inside the sandbox without loading everything into Python memory at once, the sandbox environment wraps variables in:
- **`SmartVariableList`** and **`SmartVariableDict`**
- These custom classes inherit from standard Python list/dict structures but are loaded lazily. They only open and parse the JSON files when a property (like `.keys()`, `__len__`, or iteration) is called.
- The base agent overrides Python's native `open()` and `json.loads()` inside the sandbox to seamlessly resolve these smart variables to their file references, meaning the LLM's python script runs out-of-the-box.

## 5. Model-Specific Optimizations
In [prompt_builder.py](file:///D:/Goutham_DataAgentBench/Source_Code/prompt_builder.py), GouthamAgent configures provider-specific rules:
- **Gemini models**: Appends strict instructions and warnings (like preventing the prefixing of namespace names like `default_api.` to tool calls) to avoid persistent `MALFORMED_FUNCTION_CALL` issues.
- **Claude, GPT, Kimi, and Claude-style models**: Inject tailored instructions for accessing local storage variable syntax.

## 6. Flexible CLI Run Switching
Modified [run_agent.py](file:///D:/Goutham_DataAgentBench/Source_Code/run_agent.py) to include a CLI parameter (`--agent`) allowing developers to test and benchmark the default agent side-by-side with GouthamAgent:
```bash
python run_agent.py --dataset GITHUB_REPOS --query_id 1 --agent GouthamAgent
```
